Lumax stress meter — UX / behaviour spec (seven lamps)
======================================================

CHANNELS (one lamp each, left → right)
--------------------------------------
CPU · GPU · RAM · VRAM · DISK · SWAP · NET

Asset stack: seven clip holes, seven dim layers, one gradient light — see layer_stack_authoritative.txt
(use seven everywhere; replace “six” in older notes).


COLLECTIVE VS DIRECTED
----------------------
• When the pointer is **not** over a lamp (and no menu focus override): show a **single**
  collective system stress value — mean of the seven normalized [0,1] loads — and drive the
  meter from that (all lamps follow the same level in segment styles; flow bar fills to that level).

• When the pointer **hovers** a lamp: the readout is **only** that channel (e.g. CPU). The value
  shown is a **rolling median over the last 5 seconds** of that channel, displayed as a percent
  on the **right** (e.g. “82%”).

• **Left** of the lamps: short label for the active channel while hovering (e.g. “CPU”).

• **Tooltip** (optional): keep richer detail on long hover as today.


TEXT — “GIVE THANX”
-------------------
• When the pointer **leaves the widget** entirely, show small text on the **right**: two lines,
  “Give” / “Thanx”, for **2 seconds**, then hide. Does not block interaction; cancels if the pointer
  re-enters the widget.


IMPLEMENTATION NOTES
--------------------
• GPU / VRAM: best-effort (e.g. NVIDIA SMI when present); otherwise 0% with a clear tooltip.
• Five-second median: append samples on each tick; drop samples older than 5 s; median of the rest.
• Config `focus_metric` is 0–6 when set.

BAND SWAY (5 s window)
----------------------
• Per channel, min/max spread over the last 5 s is tracked. If spread ≥ ~12% of full scale, that
  segment “band-pulses”: fill oscillates between the colours implied by min and max load (swaying
  median band). Idle strip uses per-channel levels; hover/focus still forces one channel on all lamps.

MINUTE “MAXED” ALERT
--------------------
• Defaults are conservative: ~2 min window; pegs and required maxed-fraction **differ by channel**
  (CPU / GPU+VRAM vs RAM+DISK+SWAP vs NET — see “Per-channel” below).
• Windows CPU (alert path only): the foreground process’s smoothed CPU usage is converted to the
  same 0–1 scale as total CPU load and subtracted from the measured average for “maxed” / minute
  hot logic. The strip and on-screen medians still use raw load. Optional extra dominance
  suppression (SUPPRESS_CPU_ALERT_WHEN_FOREGROUND_DOMINATES) is off by default because subtraction
  already reduces user-driven false positives.
• If enough samples in the window are at or above the peg for a channel, that meter enters hot
  state: red pulse on that lamp only (others unchanged), left label + “!” and ⚠ when not hovering.
  Hovering the red lamp (after a short delay) opens a small report + “Open Task Manager”. Flow bar:
  whole bar red-pulses when any channel is hot (idle) or when hovering a hot channel’s zone.

PER-CHANNEL “NORMAL” VS RED CARD
--------------------------------
• Each lamp may use **different** rules for what counts as healthy background noise versus a
  sustained problem. The **visible** level and rolling medians stay on **raw** telemetry unless
  the spec says otherwise; **red card** (minute maxed, hot pulse) uses a separate **alert load**
  per channel when needed.

• **CPU** — sustained high load is **harmful** to responsiveness and thermals; stricter peg + minute
  fraction; alert load subtracts foreground process CPU on the same 0–1 capacity scale (optional
  dominance suppression is separate).

• **GPU + VRAM** — **Same policy** in principle (one graphics stack): shared pegs and minute
  fractions in code. Vendor details still matter for telemetry; future: shared “foreground” or
  focused-engine attribution when available.

• **RAM, SWAP, DISK** — A **high percentage for a long time** is often **normal** (full RAM as cache,
  steady swap use, disk space “full” for data you keep). Red card is tuned **looser** than for
  processors: only **extreme sustained** pressure tends to count as maxed. What hurts the machine in
  another sense is often **I/O saturation** (reads/writes pegged) or **thrash**; future alert math
  can add signals beyond a single % (queue depth, latency, churn).

• **NET** — High up/down for long is **usually not** harmful like CPU/GPU saturation. Real risks are
  elsewhere: **metered / capped connections** (cost), and **download-heavy** use that fills **disk**
  or strains storage. Red card defaults are **very loose**; future hooks: metered flag, quota, or
  correlation with disk free space — not “bandwidth bad” by default.

Implementation: `alert_load_for_channel`, `maxed_frac_for_channel`, and
`minute_hot_fraction_for_channel` in stress_meter.py encode CPU vs GPU/VRAM vs RAM/DISK/SWAP vs NET.
