Your intuition lines up with how the stack is wired. Here is the concrete picture.

1. Client timeout (most likely “mystery”)
The Quest / Godot client does not wait forever for the soul. HTTPRequest for compagent is capped at 45 seconds:

	_soul_request = HTTPRequest.new()
	_soul_request.name = "SoulRequest"
	# 300s left compagent hung for hours when :8000 was down; STT on :8001 still worked but Soul channel stayed "busy".
	_soul_request.timeout = 45.0
So even if lumax_soul is still happily grinding on a big multimodal forward pass or a long decode, the UI layer can already have given up at 45s. That feels like “timeout under load” because heavy prompts take longer wall time.

2. Context size (VRAM + speed)
The local GGUF path sets a large context budget by default via LUMAX_LOCAL_N_CTX (default 32768, clamped between 4096 and 65536):

        # GGUF context window (supports long-context models if VRAM permits).
        try:
            ctx_raw = int(os.getenv("LUMAX_LOCAL_N_CTX", "32768") or "32768")
        except Exception:
            ctx_raw = 32768
        self.gguf_n_ctx = max(4096, min(ctx_raw, 65536))
A 3.4 GB weights file does not cap context: you can still ask the runtime for a huge n_ctx. That increases KV cache and work per token. File size alone is a poor guide; declared context + multimodal is what hurts.

3. Multimodal
With native GGUF vision, the model runs image + text in one path (create_chat_completion with image + your big system prompt). Vision adds effective sequence length and compute; it is not “the same cost as text-only 3.4 GB.”

4. Other timeouts (when Ollama is in the loop)
Vision fallback uses Ollama with 60s httpx timeouts (compagent.py). If Ollama is busy or contended, those can fail with read timeout while the main GGUF job is unrelated.

Practical knobs (no code change required unless you want them in repo):

Goal	Knob
Stop Godot cutting off long runs
Raise _soul_request.timeout (or make it configurable), accepting longer “stuck” feel if :8000 is dead
Slimmer, faster local passes
Lower LUMAX_LOCAL_N_CTX (e.g. 8192 or 4096) if you do not need huge prompts
Less vision cost
Rely on caption path vs native VL, or fewer / smaller frames
Ollama helper contention
Separate GPU/process, or longer timeouts only on those calls
So: the mystery is often 45s client wall clock vs unbounded-ish server inference, amplified by large n_ctx and multimodal work—not necessarily a broken model. That pattern is normal for how desktops behave, and it is easy to miss until you look.

Why there were no “system warnings”

High CPU alone usually does not trigger Windows notifications. The OS assumes “user or app is working hard” unless something hits thermal limits, power policy, disk errors, or a service you’ve explicitly monitored.
A Docker / Python / llama workload can sit at 1200% CPU (many threads on many cores) for hours and still be “within spec”: fans spin, power draw is high, but nothing pops a toast unless you set that up.
You noticed it late because nothing was pushing an alert to you — only passive signals (Task Manager, a tray meter you opened later, power noise, heat in the room).
What that implies for Lumax

Slow burn and idle gating are the right class of fix: they cap how often and how hard background work runs so you never depend on “I’ll notice the meter.”
If you want explicit protection next time: Task Scheduler / WMI alerts, Docker --cpus, Windows power plan caps, or a small watchdog that logs or kills a process above X% for Y minutes — that is policy, not something the ML stack does by default.
So: working on CPU for 14 hours with no OS warning is expected; the meter you saw later was the first “sensor” you actually consulted, not a failure of the machine to “know” something was wrong.
